# OpenHEXA release notes

Produce a short, readable summary of the features, fixes and chores included in a
release, aimed at the team and at users, not at developers reading a changelog.
The audience is internal colleagues who use the platform, so lead with what changes
for them in the product, not with how it was built.

## 1. Resolve the two versions

Two inputs drive everything:

- `RELEASE`: the version about to be released (e.g. `5.13.0`)
- `PRODUCTION`: the version currently running on production (e.g. `5.12.0`)

Take them from the user's request. If either is missing:

```bash
git fetch --tags --quiet
git tag --sort=-v:refname | grep -v '^frontend/' | head -10
```

- Missing `RELEASE`: use the most recent app tag, or `HEAD` if the release has not been tagged yet.
- Missing `PRODUCTION`: ask the user. Do not guess, production is often several tags behind.

App tags are bare versions (`5.13.0`). Frontend tags are prefixed (`frontend/0.61.0`)
and live in the same history, so a single range covers both.

## 2. Collect the commits

```bash
git log --oneline --no-decorate "$PRODUCTION..$RELEASE"
```

Use `$PRODUCTION..HEAD` when the release tag does not exist yet. If the tag is
missing locally, `git fetch --tags` first.

The range includes any patch releases between the two versions, which is what you
want: production is upgrading across all of them.

For more detail on an unclear commit, read the PR title and body:

```bash
gh pr view <number> --json title,body
```

`CHANGELOG.md` (generated by release-please) is a useful cross-check for what got
grouped under each version, but the git range is the source of truth.

## 3. Write the summary

Structure, following this shape:

```
**Features**

- <Theme, e.g. AI / Assistant & MCP>
    - <user-facing capability>
    - <user-facing capability>
- <Theme, e.g. Web apps>
    - <user-facing capability>
- Other
    - <one-off features that do not form a theme>

**Fixes and chores**

- <fix, one line>
- <fix, one line>
- Many package updates and security dependency bumps: <name the notable ones>
```

Rules:

- **Be succinct.** One line per item. No commit hashes, no PR numbers, no HEXA ticket IDs.
- **No em-dashes.** Use `->` when you need to point at a consequence, a comma otherwise.
- **Group features by theme** (area of the product), not by commit order. Use `Other` for the leftovers.
- **Describe the user impact**, not the implementation. "Edit web apps directly with the AI assistant", not "add mutation to webapp schema".
- **Bold anything the team must notice**, such as a change in who gets access to a feature or a required configuration change.
- **Collapse `chore(deps)` commits** into a single line, naming only the notable or security-relevant bumps.
- **Drop noise**: `chore(main): release ...` commits, revert pairs that cancel out, changes that shipped and were reverted in the same range.
- Merge several commits describing one feature into a single item.

## 4. Flag operational changes

Scan the range for anything that makes the upgrade non-trivial and call it out
under the summary:

```bash
git diff --stat "$PRODUCTION..$RELEASE" -- .env.dist docker-compose.yaml
git log --oneline "$PRODUCTION..$RELEASE" -- '*/migrations/*'
```

New environment variables, new services, or data migrations belong in the notes
even when they are invisible in the UI.
