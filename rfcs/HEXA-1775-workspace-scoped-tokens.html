Workspace tokens that stop at the workspace

A workspace token today authenticates the person, not the workspace. Holding a token for one workspace grants its owner’s full account — every workspace, every organisation, 2FA bypassed. Here is how we close that, and how we do it without anyone finding out from a broken pipeline.

The shape of the answer

Enforce scoping at a single choke point — the principal the auth middleware builds — so there is one switch and one rollback. Give tokens a real table so they can be named, listed, revoked and measured. Ship the behaviour change through a measured deprecation: observe, dry-run, opt-in, default, cutoff.

The fact that makes this tractable: every token ever issued was issued for a workspace. Cutoff means legacy tokens start being scoped, not rejected — so single-workspace users, almost certainly the majority, notice nothing.

02 · What “scoped” must mean

Scope is a reach, not a column

A scoped token may reach exactly what a member of that workspace reaches through that workspace — no more, no less.

The naïve reading — “only rows whose workspace_id matches” — is wrong, and shipping it would quietly break real features. Things that are in scope even though the row belongs elsewhere:

  • Datasets shared organisation-wide. DatasetQuerySet.filter_for_user admits shared_with_organization datasets from any workspace in an org you belong to. A token scoped to workspace-b must still see them: workspace-b can reach them, so the token can.
  • Linked datasets. DatasetLink is the cross-workspace mechanism. Scoping must respect links, not undo them.
  • The organisation, as the boundary those shares are evaluated against — but only the one the scoped workspace belongs to.
  • Pipeline templates from other workspaces, exactly as far as a member of the scoped workspace already sees them.

Out of scope, always: other workspaces, their memberships, connections, pipelines, webapps and saved queries; every account-level mutation (profile, 2FA, org membership, creating workspaces, accepting invitations); and the superuser shortcut — a superuser’s token must be no wider than anyone else’s.

This is why scoping belongs on the principal. The WIP branch gets the shape right: _scoped() is applied after every branch of filter_for_user, including the self.all() shortcuts, and Organization.filter_for_user narrows through the relation (workspaces__id=user.workspace_id) so org-shared reach survives.

03 · The choke point

One line turns it on, one setting turns it off

visibility

What rows exist for me?

WorkspaceQuerySet._scoped(), applied last so it also clamps the self.all() superuser shortcuts. Cascades to every model whose filter_for_user funnels through Workspace.objects.filter_for_user.

authority

May I act on this row?

Workspace.get_membership() returns None off-scope, so every permission derived from has_role() collapses to False — about thirty checks, all through one method.

guard

Did something reach an object out of band?

WorkspaceTokenUser.has_perm() refuses objects whose workspace isn’t the scope. Redundant by design — it catches the check somebody writes by hand next quarter.

The has_role() refactor already on the branch matters more than it looks. It converts roughly thirty hand-rolled workspacemembership_set.filter(user=…, role__in=[…]).exists() calls into one method — and that method is where scoping is enforced for the entire permission layer. Without it, scoping would need thirty correct edits, and would regress the first time someone wrote the thirty-first check by hand.

The principles this leans on, named honestly

  • One place decides reach. Everything else asks. That is what makes the change reviewable and the rollback a single setting.
  • Open/closed. WorkspaceToken is already an ABC with two strategies; a new token format arrives as a subclass, not as edits to the dispatch.
  • Liskov, via a Django proxy. WorkspaceTokenUser is a User, so every call site keeps working and just sees less. This is the decorator pattern wearing a proxy model, and it is why no resolver needs touching.
  • Fail closed. filter_for_user raising NotImplementedError for unknown principal types means a future principal class cannot silently inherit “sees everything”.
04 · Review of the WIP branch

Keep four things, fix six

Keep: the WorkspaceScopedPrincipal marker with ServicePrincipal inheriting from it — “not a person” and “confined to one workspace” were conflated and the split is right; _scoped() as a post-filter; the superuser carve-out in BaseQuerySet; and test_visibility_scoping.py, an executable invariant over an explicit model list, run twice (member holder and superuser holder). That test file is the highest-value artefact on the branch.

Fix before merge:

  1. WorkspaceTokenUser.workspace = None as a class attribute mutated per instance is fragile: a missed from_token() yields a principal whose workspace_id raises AttributeError. Make the scope a required constructor argument, or fail with a domain error that says what went wrong.
  2. core/models/base.py now imports user_management models for an isinstance check — a layering inversion. Ask the principal instead (an is_scoped property on UserInterface), so core depends on the interface.
  3. The if/elif on payload shape in authenticate() won’t survive a third format. Put an explicit version discriminator on every payload, dispatch through a registry, treat unknown as invalid.
  4. SCOPED_MODELS is hand-maintained. Add a guard test that enumerates every model with a filter_for_user and fails when one is in neither SCOPED_MODELS nor an explicit INTENTIONALLY_UNSCOPED list — otherwise the matrix silently stops being a matrix.
  5. Reconsider bypass_two_factor for tokens. At minimum a token must not perform account-level mutations (2FA settings, email change).
  6. Nothing touches the middleware yet. The wire-up is one line and belongs behind the flag in §07, not as a bare behavioural change.

And add the test cases most likely to be quietly wrong: an org-shared dataset from another workspace must stay visible, and a linked dataset must stay visible, asserted in both directions.

05 · First-class token records

membership.access_token cannot carry this change

One token per member per workspace, no name, no usage record, and revocation that breaks every copy. The migration, the UI and the measurement all need a real record:

WorkspaceAccessToken
  workspace      FK → Workspace     the scope, immutable
  user           FK → User          the identity it acts as
  name           str                "CI — nightly refresh"
  prefix         str  indexed       first 8 chars; shown in UI, greppable in logs
  token_hash     str                sha256 — the secret is shown once, never stored
  scope_version  int                1 = legacy/unscoped, 2 = scoped
  expires_at     dt   null          optional for now, cheap to add later
  last_used_at   dt   null          throttled write, once per N minutes
  last_used_ip   str  null
  revoked_at     dt   null
  revoked_by     FK → User null
  • Store a hash, not the token. Today the secret is recoverable from the database. Hashing means a DB dump is not a token dump.
  • Prefix the string (ohx_ws_…) so GitHub and GitLab secret scanning can spot leaks, and so support can identify a token from a log line without ever seeing it.
  • scope_version on the record, not inferred from payload shape, is what makes the rollout measurable and reversible per token.
  • MembershipToken keeps working untouched for the whole grandfather period; the old field is dropped only after cutoff. IdentityToken needs nothing — it is already short-lived and workspace-bound.
06 · Error semantics

The cheapest thing we can build is a good error message

Used out of scope, the architecture as it stands answers WORKSPACE_NOT_FOUND, an empty list, or a bare PERMISSION_DENIED. To a user that reads as “the platform lost my workspace” or “someone removed my permissions”, and it becomes a ticket. Return a distinct signal instead:

TOKEN_SCOPE_EXCEEDED

“This token is scoped to workspace malaria-2026 and cannot access tb-surveillance. Create a token for that workspace in Account settings → Tokens.”

The SDK and CLI surface that message verbatim and link the migration page. Every occurrence is logged with the token prefix, which is what lets the admin report in §07 say “three of your tokens hit scope errors this week”.

Disclosing “this exists but you can’t have it” is fine here: the holder already knows their own workspace list, so we reveal nothing they couldn’t learn by logging in. Silent emptiness trades a negligible security gain for a large support cost.

07 · Rollout

No user learns about this from a broken pipeline

Each phase has an entry gate, an exit gate and a rollback. Because enforcement lives in the principal, every phase up to and including cutoff is one setting away from off.

  1. 00

    Instrument — no behaviour change

    Land the token table, backfill one record per existing access_token at scope_version = 1, and record last_used_at / IP / user agent on every token request. Then add shadow evaluation: on each request, compute whether a scoped principal would have answered differently and log {token_prefix, workspace, operation, would_deny}.

    Exit — two weeks of data. We can then answer, per organisation: how many tokens are live, how many are used at all, and how many ever act outside their workspace.

    Non-negotiable. Every estimate of “how much will this break” is currently a guess, and the fix is two weeks of logging.

  2. 01

    Dry-run enforcement

    Wire the middleware to build a WorkspaceTokenUser, behind a three-state setting: off / log / enforce, defaulting to log. In log the request proceeds unscoped and every would-be denial is recorded and attributed.

    Exit — the would-deny rate is understood and each remaining pattern has an owner: either the scope semantics are wrong (probably org-shared datasets) or a user integration needs migrating, and we know whose.
  3. 02

    Scoped tokens available, opt-in

    Account settings → Tokens gains named, per-workspace token creation at scope_version = 2. Existing tokens display as Legacy — full account access with a “Replace with a scoped token” action. Ship an SDK/CLI that understands the new prefix and warns on a legacy token; publish the minimum version. Docs, changelog, migration guide.

    Exit — create / rotate / revoke works end to end, docs are live, SDK released.
  4. 03

    Scoped by default

    generateWorkspaceToken mints scoped tokens; legacy tokens still work. Banner for users holding a legacy token used in the last 30 days — don’t nag people whose tokens are dormant, nag them at revocation time instead. Add an org-admin view: holder, workspace, last used, scoped or legacy. That view is what lets an admin drive their own migration instead of waiting for us.

    Exit — legacy usage trending down, and the remaining holders are known by name.
  5. 04

    Nudge, with dates

    Email the holders of legacy tokens in use — token name, workspace, last-used date, cutoff date. Then two announced brownouts: one hour of enforcement on day X and day Y. A brownout converts “I ignored the email” into a survivable 60-minute incident instead of a surprise outage. Pick the slot against the actual pipeline schedule data, not against our timezone.

    Exit — brownouts produce no unexplained failures.
  6. 05

    Cutoff

    All tokens enforce their scope. Legacy tokens are scoped, not rejected — a MembershipToken already names its workspace, so it starts behaving as a token for that workspace rather than dying. Genuinely cross-workspace automation needs one token per workspace, which the CLI config already models per workspace. Offer a per-organisation grace extension, once, with a hard expiry, so one unlucky team can’t hold the platform.

    Then — drop membership.access_token, remove the flag, delete the dry-run code.
08 · The user’s side

Seven ways to find out, in descending order of preference

  1. They read the changelog. (Few.)
  2. The token list marks theirs Legacy — full account access.
  3. A banner, because a token of theirs was used recently.
  4. Their org admin tells them, from the org token report.
  5. An email naming the token and the cutoff date.
  6. A brownout fails a run — with an error that names the problem and the fix.
  7. Cutoff day. Nobody should reach here.

What the token UI has to show

Name, workspace, scoped-or-legacy badge, created date, last used, revoke. “Last used” is what lets someone delete a token fearlessly — and fearless deletion is where the security benefit actually comes from.

The honest cost, and how we pay it down

Someone automating three workspaces now needs three tokens. Mitigations in order: the CLI already stores tokens per workspace; make creating one two clicks from the workspace page as well as from account settings; allow creating several at once for the workspaces you pick; and never silently invalidate — creating a new token must not kill the old one, which today it does, and which is a bug worth fixing early regardless.

There is a real benefit — say it

Scoped, named, revocable tokens with last-used dates mean you can hand a token to a CI job or a collaborator without handing over your account, rotate one integration without breaking the others, and let an admin see and revoke what exists. Put that in the changelog, not “tokens are now restricted”.

10 · Open questions

What I need from you

  1. What does the SDK/CLI actually query? The blast radius hinges on whether it ever calls workspaces or me { workspaces } with a token. My assumption is that config is per workspace, so the damage is small — worth a pass over openhexa-cli, because it changes the whole risk picture.
  2. Should a token be able to act as less than its owner (read-only, role cap)? Out of scope by decision, but a nullable max_role column costs nothing now and buys the option.
  3. A workspace bot identity? Letting an admin mint a token for a service identity in their workspace, rather than for themselves, is arguably the real answer for CI — it removes “my token, my account” entirely. Bigger change; flag as follow-up.
  4. Maximum lifetime on scoped tokens from day one — e.g. one year? Much cheaper to introduce now than later.
  5. bypass_two_factor — keep, restrict, or drop for tokens?
  6. Who owns the cutoff date and the comms? Needs product sign-off before Phase 3, not after.
  7. Do internal tools depend on a wide token today? If yes, they need an alternative before Phase 5.
11 · Alternatives considered

And why not

OptionWhy not
Per-request workspace header — token stays wide, client declares intentClient-declared scope isn’t a security boundary; a leaked token just omits the header
JWT with claims instead of signed opaque payloadsReal benefits, bigger change, and no revocation without a denylist. The signed-payload strategy already in place is adequate once the token table gives us revocation
Capability tokens now (read-only, pipeline-only)Doubles the permission surface while the primary hole is still open. Ship workspace scoping; keep the extension point
Enforce in each resolver~200 resolvers, every one a chance to forget, unreviewable, and no single rollback switch
Hard cut in one releaseFastest to a clean codebase, and the one option guaranteed to break users without warning
Do nothing, document the riskThe token is an account credential in a place users treat as a project credential. That gap doesn’t stay theoretical
12 · What I’d do next

Concretely, in this order

  1. Finish the branch’s enforcement wiring behind the three-state flag, defaulting to off.
  2. Land WorkspaceAccessToken + backfill + last_used_at. It blocks every measurement and every UI decision downstream.
  3. Add shadow-evaluation logging and let it run for two weeks.
  4. In parallel, fix the six review items and add the org-shared / linked dataset tests — the places most likely to be quietly wrong.
  5. Bring the Phase 0 numbers to product, and only then pick a cutoff date.
