Appendix A1 · from slide 05

Three layers, three different questions

LayerQuestionMechanism
visibility What rows exist for me? WorkspaceQuerySet._scoped(), applied after every branch — so it also clamps the self.all() superuser shortcuts. Cascades to every model whose filter_for_user funnels through Workspace.objects.filter_for_user.
authority May I act on this row? Workspace.get_membership() returns None off-scope, so every permission built on has_role() collapses to False — about thirty checks, one method.
guard Did something reach an object out of band? WorkspaceTokenUser.has_perm() refuses objects outside the scope. Redundant on purpose — it catches the check somebody writes by hand next quarter.

The has_role() refactor is what makes this possible: it replaced ~30 hand-rolled workspacemembership_set.filter(user=…, role__in=[…]).exists() calls with one method. Without it, scoping would need thirty correct edits and would regress on the thirty-first.

Appendix A2 · from slide 04

Reach, not rows — the full map

In scope, even when the row belongs to another workspace:

  • Datasets shared organisation-wide. DatasetQuerySet.filter_for_user admits shared_with_organization datasets from any workspace in an org you belong to.
  • Linked datasets. DatasetLink is the cross-workspace mechanism — scoping must respect links, not undo them.
  • The organisation, as the boundary those shares are evaluated against — but only the one the scoped workspace belongs to.
  • Pipeline templates from other workspaces, exactly as far as a member of the scoped workspace already sees them.
  • The SDK has a caller for this. workspace.get_dataset(…, source_workspace_slug=…) resolves datasetLinkBySlug against the source workspace (datasets/schema/queries.py:72-78) — so this is a live code path, not a hypothetical.

Out of scope, always:

  • Other workspaces and their memberships, connections, pipelines, webapps, saved queries.
  • Every account-level mutation — profile, 2FA, org membership, creating workspaces, accepting invitations.
  • The superuser shortcut. A superuser’s token is no wider than anyone else’s.

The implementation detail that keeps this honest: Organization.filter_for_user narrows through the relation (workspaces__id=user.workspace_id), not by dereferencing the workspace — so org-shared reach survives while org administration doesn’t.

Appendix A3 · from slide 05

Why the principal, and not request.workspace

The authorization API has two shapes, and neither takes a request:

Model.objects.filter_for_user(user)   210 sites
user.has_perm(perm, obj)             363 sites

has_perm routes through Django’s auth backend, whose signature is fixed at (user_obj, perm, obj). The request is not in scope there and never will be.

So a request-based scope means either threading an argument through ~570 call sites, or ambient thread-local state the model layer reads implicitly.

And it wouldn’t cover everything. filter_for_user is also called with no request at all — data_studio/query_runner.py, workspace_copier/, core/search.py, the connector credential modules. A request-based scope is silently absent there, and absent means unscoped.

What we keep request.workspace for: telemetry. It’s the natural key for the shadow log and the scope-error metric, and it makes the scope visible in traces. It just isn’t the enforcement mechanism.

The cost: request.user is no longer plainly a User. Proxy identity shows up in audit logs and anything asserting the concrete class, and per-user caches need the scope in their key.

Appendix A4 · from slide 06

The token record

WorkspaceAccessToken
  workspace      FK → Workspace   the scope, immutable
  user           FK → User        the identity it acts as
  name           str              "CI — nightly refresh"
  prefix         str  indexed     shown in UI, greppable
  token_hash     str              sha256, shown once
  scope_version  int              1 legacy · 2 scoped
  expires_at     dt   null
  last_used_at   dt   null        throttled write
  last_used_ip   str  null
  revoked_at     dt   null
  revoked_by     FK → User null

Why not keep membership.access_token: one token per member per workspace, no name, no usage record, and revocation that breaks every copy. It can’t carry the migration, the UI, or the measurement.

Hash, don’t store. Today the secret is recoverable from the database. Hashing means a DB dump is not a token dump.

Prefix the string (ohx_ws_…) so GitHub and GitLab secret scanning spot leaks, and so support can identify a token from a log line without ever seeing it.

scope_version on the record, not inferred from payload shape, is what makes the rollout measurable and reversible per token.

Appendix A5 · from slide 11

The error is part of the migration

Out of scope today gives WORKSPACE_NOT_FOUND, an empty list, or a bare PERMISSION_DENIED. To a user that reads as “the platform lost my workspace” — and becomes a ticket. What we return instead:

TOKEN_SCOPE_EXCEEDED
This token is scoped to workspace malaria-2026 and cannot access
tb-surveillance. Create a token for that workspace in
Account settings → Tokens.

The SDK and CLI surface it verbatim and link the migration page. Every occurrence is logged with the token prefix — which is what lets the org-admin report say “three of your tokens hit scope errors this week”.

And it must not be UNAUTHENTICATED. The CLI collapses any error carrying that code into InvalidTokenError (cli/api.py:213-215), so the user would be told their token is invalid and would regenerate it — the wrong fix, applied confidently. A distinct code is a requirement, not a nicety.

On disclosure: saying “this exists but you can’t have it” is fine here. The holder already knows their own workspace list, so we reveal nothing they couldn’t learn by logging in. Silent emptiness trades a negligible security gain for a large support cost.

Appendix A9 · from slide 11

How a brownout actually works

Why do it

  • Emails get ignored. A failed run at 10:00 on an announced Tuesday does not.
  • Failure is recoverable — a nightly pipeline can be re-run the same day. The identical failure on cutoff day is an outage with no fallback.
  • It rehearses the enforce path in production before it is permanent.
  • It turns “we think a few tokens still cross workspaces” into a list of names.

Blast radius is bounded by construction: only token-authenticated requests are affected. Everyone in the web UI sees nothing.

What it costs to build: nearly nothing

A brownout is not a feature, it is a schedule — and the lever already exists: Feature / FeatureFlag (user_management/models.py:840-865), with force_activate as a global switch in Django admin. No deploy, no restart.

  • has_feature_flag is an uncached query per call — memoise it before putting it in the auth path.
  • A boolean can’t express off / log / enforce: use a small model with a mode plus an enforce_from/until window, so brownouts run themselves.
  • No scheduler in config/settings/base.py — a timed flip means a CronJob, or a person.

The hard parts aren’t code: the hour (real pipeline schedules, many timezones), the comms, no auto-retry of failed runs, and someone watching the metric.
